당신은 단순히 UI를 생성하는 AI가 아니라, **독립 디지털 프로덕트 디자인 스튜디오의 Lead Product Designer + iOS Design Engineer** 역할을 맡는다.

아래 기획을 기반으로 iPhone 앱의 전체 디자인 방향과 Design System을 설계하고, 이후 실제 SwiftUI 구현까지 자연스럽게 연결될 수 있는 수준으로 정리하라.

이 작업에서 가장 중요한 목표는 다음이다.

> “AI가 자동 생성한 생산성 앱”처럼 보이지 않는 것.
>
> Dribbble용 컨셉 디자인이 아니라, 실제 디자인 에이전시가 제품의 성격을 해석하고 오랜 기간 유지할 수 있도록 설계한 제품처럼 보여야 한다.

---

# 1. Product Context

서비스명은 현재 **「한 주」**라는 가칭을 사용한다.

이 앱은 집안일과 공부 등의 루틴을 주간 단위로 계획하고 실제 실행까지 이어갈 수 있도록 돕는 개인용 iOS 앱이다.

핵심 흐름:

루틴 등록
→ 일요일 다음 주 계획
→ 요일별 배치
→ 당일 알림
→ 실행 또는 완료
→ 필요하면 일정 조정
→ 짧은 회고
→ 다음 주 계획

핵심 화면:

- 오늘
- 이번 주
- 루틴함
- 기록
- 설정

초기 플랫폼:

- iPhone
- SwiftUI
- SwiftData
- UserNotifications
- EventKit
- 서버 없는 Local-first 구조

Mac 지원 및 동기화는 후속 버전이다.

---

# 2. Product Philosophy

이 앱을 일반적인 Habit Tracker나 Todo App처럼 디자인하면 안 된다.

사용자에게 다음과 같은 감정을 주어서는 안 된다.

- 밀린 일이 쌓이고 있다는 압박
- 계획을 지키지 못했다는 죄책감
- 스트릭이 끊겼다는 실패감
- 낮은 완료율에 대한 평가
- 지속적인 푸시와 재촉
- 게임에서 퀘스트를 실패한 것 같은 경험

이 앱은 사용자를 관리하거나 평가하지 않는다.

대신:

- 계획은 언제든 바꿀 수 있다.
- 하지 못한 일은 빚이 아니다.
- 쉬어도 된다.
- 기록하지 않아도 된다.
- 다시 시작하기 쉬워야 한다.
- 작은 행동도 실제로 한 행동이라면 가치가 있다.

따라서 UX Writing과 Visual Design 모두

**Calm / Flexible / Human / Quiet / Warm / Trustworthy**

라는 인상을 가져야 한다.

그러나 지나치게 감성적인 명상 앱이나 귀여운 습관 앱처럼 만들어서도 안 된다.

---

# 3. Desired Design Character

제품 전체의 디자인 방향을 다음 키워드로 정의한다.

## Calm Productivity

생산성 도구이지만 긴장감이 낮아야 한다.

## Editorial Utility

단순한 카드 UI 모음이 아니라
정보의 크기, 여백, 타이포그래피와 배치 자체로 위계를 만든다.

잡지의 Editorial Layout과 잘 설계된 Utility App의 중간 지점을 지향한다.

## Soft Precision

기능적으로는 정밀하지만 시각적으로는 공격적이지 않아야 한다.

## Native but Distinctive

Apple HIG를 존중하지만
“기본 SwiftUI 컴포넌트를 그냥 붙여놓은 앱”처럼 보여서는 안 된다.

별도의 Brand Character가 있어야 한다.

# 4. 반드시 피해야 하는 “AI Generated UI” 패턴

다음 표현을 기본 스타일로 사용하지 마라.

- 화면마다 큰 gradient background
- 보라색/파란색 AI gradient
- glassmorphism 남용
- glow
- neon
- 모든 요소를 둥근 카드 안에 넣는 구조
- 카드 안의 카드
- 과도하게 큰 border-radius
- 모든 행마다 아이콘
- 의미 없는 decorative icon
- Hero dashboard
- 원형 progress chart
- donut chart
- streak flame
- XP / Level / Point
- 거대한 숫자로 표시한 완료율
- 과도한 shadow
- floating blob
- 지나치게 많은 pill
- 모든 텍스트에 색을 부여하는 방식
- “Good morning 👋” 같은 템플릿형 생산성 앱 문구
- AI가 자주 만드는 3-column metric dashboard 패턴
- 아무 의미 없는 illustration
- 화면마다 동일한 card stack 반복
- 너무 많은 색상
- 지나치게 친절한 설명문

UI를 풍성하게 보이게 하기 위해 장식을 추가하지 마라.

**정보 구조, 타이포그래피, 간격, alignment, interaction으로 완성도를 만들어라.**

# 5. 먼저 Visual Direction부터 설계하라

화면부터 구현하지 말고 먼저 전체 Visual Language를 정의한다.

다음 순서로 설계한다.

## A. Brand Personality

5~7개의 Brand Attribute를 정의한다.

각 항목에 대해:

- 의미
- UI에서 어떻게 표현되는지
- 피해야 하는 반대 표현

을 작성한다.

예:

Calm
→ 낮은 채도
→ 충분한 whitespace
→ 강한 경고색 남용 금지

이런 방식이다.

# 6. Color System

컬러부터 임의로 여러 개 만들지 않는다.

다음 구조의 Semantic Color System을 설계하라.

### Neutral

- background
- surface
- surfaceRaised
- textPrimary
- textSecondary
- textTertiary
- separator

### Brand

하나의 Primary Accent를 중심으로 구성한다.

Primary 색은 생산성 앱에서 흔히 사용하는 강한 파란색이나 보라색보다
조금 더 생활 친화적이고 차분한 방향을 탐색한다.

예를 들어 다음 계열을 후보로 검토할 수 있다.

- muted green
- sage
- olive
- warm blue
- muted indigo
- warm charcoal + accent

단, 그대로 채택하지 말고 제품 철학에 가장 적합한 방향을 선택한다.

### Semantic

- success
- warning
- destructive
- calendar
- paused

상태 색은 최소한으로 사용한다.

특히:

미완료 ≠ Error

이므로 미완료 상태에 빨간색을 사용하지 않는다.

Skip 또한 실패 상태가 아니다.

Dark Mode까지 고려하여 semantic token으로 정의한다.

색상은 실제 구현 가능한 Hex 또는 SwiftUI Color Asset 기준으로 작성한다.

# 7. Typography

Typography가 이 앱의 주요 시각적 Identity 중 하나가 되어야 한다.

iOS에서 실제 구현 가능한 구성을 사용한다.

가능하면 SF Pro / System Font를 기반으로 하고
font weight, size, spacing을 정교하게 조절해 브랜드 느낌을 만든다.

최소한 다음 typography token을 정의한다.

- Display
- Large Title
- Title
- Section Title
- Body
- Body Emphasis
- Secondary
- Caption
- Meta

각각:

- font size
- weight
- line height
- 사용 위치

를 정의한다.

큰 제목을 남발하지 않는다.

숫자와 날짜는 필요하면 monospacedDigit 사용을 고려한다.

# 8. Spacing & Layout System

랜덤한 padding을 사용하지 않는다.

4pt 또는 8pt 기반 spacing system을 만든다.

예:

4 / 8 / 12 / 16 / 24 / 32 / 48

그리고 각각에 의미를 부여한다.

화면 좌우 margin도 고정된 규칙을 만든다.

또한:

- section gap
- list item gap
- inline gap
- modal padding
- bottom safe-area spacing

을 정의한다.

Whitespace는 장식이 아니라 UI hierarchy를 만드는 핵심 요소로 사용한다.

---

# 9. Radius / Border / Elevation

AI UI의 가장 흔한 문제인 과도한 rounded card를 방지한다.

Corner Radius를 2~3단계만 사용한다.

예:

- control
- container
- modal

Shadow 사용은 매우 제한한다.

가능하면:

- background contrast
- separator
- spacing

을 통해 hierarchy를 만든다.

Border도 필요한 곳에만 사용한다.

# 11. 화면별 Information Hierarchy

모든 화면을 같은 레이아웃으로 만들지 마라.

화면마다 목적에 맞는 위계가 있어야 한다.

## 오늘

이 앱에서 가장 자주 보는 화면.

가장 중요한 질문은:

> “오늘 나는 무엇을 하면 되는가?”

상단에 통계 Dashboard를 배치하지 않는다.

오늘 날짜와 오늘의 실행 항목을 중심으로 한다.

항목은:

- 예정
- 진행 중
- 완료

상태를 시끄럽지 않게 구분한다.

실행 중인 하나의 루틴은 다른 항목보다 명확하게 강조한다.

주요 Action:

시작

또는 실행 중이라면:

일시 정지 / 완료

완료된 항목은 시각적으로 사라지지 않지만
현재 해야 할 일보다 hierarchy를 낮춘다.

---

## 이번 주

캘린더 앱처럼 복잡한 Grid를 그대로 복제하지 않는다.

iPhone 한 손 사용성을 고려한다.

Monday → Sunday 흐름이 명확해야 한다.

각 날짜에 대해:

- 계획한 루틴
- 예상 시간
- 시간 지정 여부

를 빠르게 파악할 수 있어야 한다.

요일별 총 예상 시간은 보여줄 수 있지만
“목표 대비 부족/초과”처럼 평가하지 않는다.

일정 이동은 자연스럽고 가벼운 Interaction으로 설계한다.

Drag & Drop을 사용할 경우
모바일에서 실패하기 쉬운 동작이 되지 않도록
Tap 기반 Reschedule도 함께 제공한다.

---

## 루틴함

루틴을 관리하는 Repository다.

Todo Inbox처럼 복잡하게 만들지 않는다.

루틴의 핵심 정보:

- 이름
- 카테고리
- 예상 시간
- 기본 횟수

가 자연스럽게 보이도록 한다.

모든 속성을 목록에서 노출하지 않는다.

등록 과정 역시 Form 화면보다
가볍게 하나씩 입력하는 느낌을 우선한다.

---

## 기록

Analytics Dashboard가 아니다.

과거의 나를 평가하는 곳이 아니라
“실제로 내가 무엇을 했는지” 확인하는 공간이다.

우선순위:

1. 완료한 일
2. 실제 기록 시간
3. 루틴별 실행 횟수
4. 주간 메모

Charts는 반드시 필요한 경우에만 사용한다.

원형 완료율 그래프는 사용하지 않는다.

“이번 주 63% 성공” 같은 표현도 사용하지 않는다.

대신:

이번 주에 한 것
공부한 시간
다시 미룬 뒤 해낸 것

등 실제 행동을 보여준다.

---

## 설정

기능 중심으로 단순하게 구성한다.

- 계획 알림
- 실행 알림
- 기본 알림 시간
- Apple Calendar
- 권한 상태

설정 화면에 브랜드 표현을 과도하게 넣지 않는다.

# 12. UX Writing

문구는 짧고 사람답게 작성한다.

명령보다는 제안을 선호한다.

BAD

“Task incomplete”

“3 tasks overdue”

“You failed to complete your goal”

“Keep your streak!”

GOOD

“오늘은 여기까지”

“다른 날에 해도 괜찮아요”

“이번 주에서는 건너뛸까요?”

“지금 시작할까요?”

단, 모든 문구를 감성적으로 만들지는 않는다.

Functional UI에서는 간결성을 우선한다.

# 13. Empty State

Empty State에 큰 illustration을 자동으로 넣지 않는다.

텍스트 + 필요한 경우 작은 symbol 정도만 사용한다.

예:

오늘 예정된 일이 없는 경우

“오늘은 정해둔 일이 없어요.”

Secondary:

“필요하면 이번 주 계획에서 추가할 수 있어요.”

CTA:

“이번 주 보기”

같은 방식이다.

---

# 14. Motion & Interaction

Motion은 제품의 완성도를 높이는 중요한 요소다.

하지만 “예쁜 애니메이션”을 보여주기 위한 animation은 만들지 않는다.

Motion Principle:

- spatial continuity
- feedback
- state transition
- hierarchy

에만 사용한다.

예:

루틴 시작
→ 해당 row가 자연스럽게 Active Routine 영역으로 이동

완료
→ check animation 후 completed section으로 이동

요일 이동
→ 이전 위치에서 새로운 날짜로 자연스럽게 transition

Sheet
→ native iOS presentation 유지

추천 duration:

약 180~350ms

과도한 spring/bounce는 피한다.

Haptic Feedback도 주요 action에 제한한다.

---

# 15. Iconography

SF Symbols를 기본으로 사용한다.

아이콘은 의미가 있을 때만 사용한다.

텍스트만으로 충분한 Action에 습관적으로 아이콘을 붙이지 않는다.

특히:

Calendar
Timer
Pause
Play
Check
Bell

같이 즉시 이해되는 기능에서 사용한다.

Category마다 emoji를 강제하거나
각 루틴에 임의의 colorful icon을 넣지 않는다.

# 16. Accessibility

최소한 다음을 고려한다.

- Dynamic Type
- VoiceOver label
- 44pt 이상의 tap target
- 색만으로 상태 구분 금지
- Reduce Motion
- 충분한 contrast
- Dark Mode

Accessibility 대응 때문에 디자인을 나중에 변경하지 않도록
Design System 단계에서 포함한다.

# 18. Design System Code Architecture

실제 SwiftUI 프로젝트로 구현할 수 있도록 다음 구조를 고려한다.

DesignSystem/
├── Foundation/
│   ├── AppColor.swift
│   ├── AppTypography.swift
│   ├── AppSpacing.swift
│   ├── AppRadius.swift
│   └── AppMotion.swift
│
├── Components/
│   ├── Button/
│   ├── Routine/
│   ├── Planning/
│   ├── Input/
│   └── Feedback/
│
└── Extensions/

가능하면 magic number를 View 내부에 직접 사용하지 않는다.

예:

.padding(.horizontal, AppSpacing.screen)

처럼 일관된 token을 사용한다.

그러나 모든 값을 추상화해 불필요하게 복잡한 Design System을 만들지도 않는다.

MVP 규모에 맞게 유지한다.

---

# 19. Design Hierarchy Rule

모든 화면에서 다음 순서를 지킨다.

1. 지금 사용자가 알아야 하는 것
2. 지금 할 수 있는 Action
3. 보조 정보
4. 과거 상태
5. 설정이나 상세 정보

Color보다:

- position
- whitespace
- type size
- weight

를 먼저 사용해 hierarchy를 만든다.

Accent Color는 Action과 의미 있는 상태에만 사용한다.

---

# 20. Visual Density

앱을 지나치게 sparse하게 만들지 않는다.

“미니멀 디자인 = 큰 여백 + 요소 2개”가 아니다.

정보량은 충분히 유지하되
alignment와 grouping을 사용해서 정돈한다.

# 24. 최종 목표

이 제품을 처음 본 사람이

“예쁜 생산성 앱”

이라고 생각하는 것보다,

“이 앱은 사용자를 압박하지 않는 방식까지 고민해서 만들어졌구나.”

라고 느끼게 만들어라.

화려함보다 제품의 태도를 디자인한다.

UI 트렌드를 조합하지 말고
제품의 철학에서 시각 언어를 도출한다.

그리고 그 시각 언어가 모든 화면, 컴포넌트, 애니메이션과 UX Writing에 일관되게 적용되도록 한다.
